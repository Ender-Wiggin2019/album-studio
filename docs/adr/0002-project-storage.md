# ADR 0002：项目文档与图片存储

- 状态：已接受
- 决策日期：2026-08-15
- 更新日期：2026-08-16

## 背景

相册需要处理大量原图、可撤销的非破坏性编辑和多种尺寸的渲染资源。将图片塞入单个文档会放大读写与内存成本，也无法让桌面文件系统和浏览器存储共享清晰的数据边界。

## 决策

产品只使用严格的 `AlbumDocument` schema v2。文档保存项目 `PageSpec`、素材元数据、页面、按数组顺序排列的 `Block`、主题和 revision。三类 Block 分别保存图片编辑参数、受限富文本文档或内置装饰资源 ID；文档不保存 Base64 图片或任意绝对素材路径。

桌面端将一个项目保存为：

```text
名称.album-project/
├── manifest.json
├── assets/
│   ├── original/<sha256>.<ext>
│   └── cache/<pipeline-version>/<sha256>/<variant>-<size>.webp
└── backups/manifest-r<revision>-<timestamp>.json
```

- 原图按 SHA-256 内容寻址并去重，始终保持不变。
- 缩略图、预览图和打印图是可重建缓存，不是权威数据。
- 写入使用同目录临时文件、`fsync` 和原子改名；保存按项目串行，并拒绝过期 revision。
- 自动保留最近 5 份 manifest 备份。
- 所有路径在访问前完成 realpath、符号链接和项目根边界校验。

浏览器端在当前站点来源的 OPFS 下使用 `album-studio/projects/<id>` 保存同一文档语义和内容寻址素材。浏览器请求持久存储，但不承诺配额永久存在，也不直接打开桌面 `.album-project` 目录。

图片管线在桌面端使用 `sharp`，在浏览器端使用 `createImageBitmap`、`pica` 与 `hash-wasm`。两端都限制 8000 万像素和 2 个并发衍生任务，并及时释放临时资源。

## 结果

- 项目文档保持小而可校验，原图可复用，衍生资源可按需重建。
- 桌面项目目录可以整体复制、备份和离线打开，源照片不会被改写。
- 浏览器端获得轻量、本地优先的调试与使用方式，但用户清除站点数据时项目会丢失。
- schema 入口保持单一且严格；旧 image-only 格式不迁移、不回退，未来格式升级也必须通过新的显式版本决策完成。
